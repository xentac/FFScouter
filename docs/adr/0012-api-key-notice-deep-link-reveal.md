# API key notice deep-link: explicit reveal after render, no forced scroll

The faction-page banner that nudges users with no (or invalid) API key links to `profiles.php` with an explicit XID and a `#ff-scouter-api-key` marker, expecting the [[Settings Panel]] to expand and surface its API Key field. The obvious-looking approach — just link to `profiles.php?XID=<id>#ff-scouter-api-key` and let the browser's native "expand a closed `<details>` and scroll to it when the URL fragment targets an element inside it" behavior handle the rest — does not work here, on any browser, PDA included: the fragment is processed at navigation time, but the panel (and its `#ff-scouter-api-key` input) is constructed and inserted asynchronously by `settings/index.ts` afterward, well after the browser has already given up looking for that id. So the reveal has to be driven explicitly, after the panel exists.

`settings/index.ts` already exposes `panel.updateComplete` (a promise resolved from the React tree's `onRendered` callback, i.e. after commit — see the class body in `settings-panel.tsx`). After inserting the panel, if `location.hash === "#ff-scouter-api-key"`, we `await panel.updateComplete` and then set the `<details>` element's `open` attribute directly — no new lifecycle hook needed, no `scrollIntoView` call. Auto-scrolling on arrival was considered and deliberately rejected: yanking the viewport on page load is a UX pattern we don't want in this codebase regardless of whether it would technically work. Because the panel is injected immediately after `.profile-wrapper`, near the top of profile-page content, simply expanding it in place is enough to put the API Key field in or near the initial viewport without any programmatic scroll.

## Considered Options

- **Native fragment-in-`<details>` browser behavior only**: rejected — the target element doesn't exist in the DOM at navigation time, so no browser fires this regardless of engine/version.
- **`scrollIntoView` on the API Key input once revealed**: rejected — deliberate policy against script-driven scroll-jacking, independent of whether it's technically reliable.
- **Bare `profiles.php` (no XID) as a fallback link when `getLocalUserId()` fails/times out**: rejected — confirmed this 404s rather than resolving to the logged-in user's own profile. The banner's link falls back to plain, non-clickable text in that case instead of shipping an unverified URL.
